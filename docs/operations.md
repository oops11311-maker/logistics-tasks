# 물류자동화 업무 운영

이 문서는 코드와 이 환경에서 확인한 사실만 적습니다. 앱은 이 작업에서 배포하지 않았습니다.

## 로그인

사람 화면과 업무 API는 세션 쿠키가 있어야 합니다. 예외는 `/login`, `/setup`, `POST /api/auth/login`, `GET /api/auth/admin-setup`, `POST /api/auth/admin-setup`, `GET /api/health`뿐입니다. 봇 API와 스케줄 웹훅은 토큰만 받습니다. Cursor 신원으로 로그인하거나 이름·이메일을 덮어쓰지 않습니다.

사용자 이름은 이메일이 아니어도 되고, 단계 안에서 유일합니다. 로그인은 그 사용자 이름을 씁니다. 관리자는 관리 화면에서 계정 사용자 이름을 바꾸거나 비어 있던 이름을 넣을 수 있습니다. 같은 단계에 이미 있으면 거절합니다. 사용자 이름을 바꿔도 세션은 끊기지 않습니다. 세션은 멤버 번호와 비밀번호 버전에 묶여 있고, 다음 로그인부터 새 이름을 씁니다. 비밀번호는 scrypt 해시만 저장합니다. 로그인 시도는 사용자 이름과 IP로 제한합니다. 세션은 데이터베이스에 있고 12시간 뒤 만료됩니다. 쿠키는 HttpOnly, Secure, SameSite=None, Partitioned입니다. 비공개 게이트가 앱을 iframe에 넣을 때도 같은 프레임의 다음 요청에 실립니다. 비밀번호 변경, 관리자의 비밀번호 초기화, 계정 비활성화는 기존 세션을 끊습니다. 쿠키 세션의 변경 요청은 `x-csrf-token`이 필요합니다.

`migrations/005_admin_username.sql`은 이메일 또는 사용자 이름이 기존 관리자 주소인 행의 사용자 이름을 `limjaeyeol`로 바꿉니다. 이미 그 이름이면 다시 쓰지 않습니다. 다른 행이 그 이름을 쓰고 있으면 그 이름만 비우고, 멤버 행과 담당 업무는 지우지 않습니다.

관리자가 계정을 만들고 처음 비밀번호를 지정합니다. 이메일 초대는 로그인으로 이어지지 않습니다. 처음 비밀번호나 초기화된 비밀번호로 들어오면 다른 업무를 보기 전에 비밀번호를 바꿔야 합니다.

`limjaeyeol`의 비밀번호 해시가 비어 있으면 `/login`으로 들어온 문서 요청을 미들웨어가 `/setup`으로 보냅니다. 이 이동은 페이지를 그리기 전에 그 요청의 신원을 읽습니다. `/setup` 문서에서 **최초 관리자 비밀번호 설정**이 한 번 열립니다. 해시가 이미 있으면 `/setup`은 폼 대신 이미 설정되었다고만 알리고, 로그인 폼은 `/login?form=1`입니다. 그 사람이 비밀번호와 확인 값을 넣고, 10자 이상이면 scrypt 해시만 저장합니다. 저장은 `password_hash`가 비어 있을 때만 되고, 동시에 두 요청이 와도 한 번만 성공합니다. 설정된 뒤에는 화면이 닫히고 다시 열리지 않으며, 같은 API는 거절됩니다. 그 다음부터는 사용자 이름 `limjaeyeol`과 방금 정한 비밀번호로 로그인합니다. 이 단계는 세션을 만들지 않고, 이름과 이메일을 바꾸지 않습니다.

이 단계는 `cursor/identity.js`의 `getIdentity`가 그 문서 요청에서 서명한 사람 신원이고, 이메일을 소문자로 맞춘 값이 `oops11311@gmail.com`일 때만 열립니다. `emailVerified`가 참이 아니어도, 서명이 확인되고 이메일이 같으면 열립니다. 그 경우 서버 로그에는 `admin_setup_email_unverified`만 남습니다. 서명이 없거나, 이메일이 다르거나, 헤더를 위조하면 단계는 숨고 API는 거절됩니다. 거절 이유는 `admin_setup_closed`와 이유 코드만 로그에 남고, 토큰, 이메일, 비밀번호 해시는 남기지 않습니다. 로컬의 시뮬레이트된 신원(`simulated`)과 API 키는 서명된 사람이 아니므로 거절됩니다. 폼은 문서 POST로 보냅니다. 숨은 `csrf` 값은 서버 키로 서명한 필드이고, 만료 시각이 들어 있습니다. 확인은 그 서명만 보며 쿠키가 돌아오지 않아도 됩니다. 서명이 없거나, 바뀌었거나, 만료되면 거절합니다. JSON API는 같은 값을 `x-csrf-token`으로 보냅니다. 로그인 POST는 쿠키를 읽지 않습니다. 로그인이 심는 세션 쿠키도 SameSite=None, Partitioned입니다. IP당 분당 20회로 제한합니다. `INITIAL_ADMIN_PASSWORD`는 더 이상 읽지 않습니다.

`GET /api/health`의 `commit`은 호스트가 `VERCEL_GIT_COMMIT_SHA` 또는 `CURSOR_GIT_COMMIT`을 넣을 때만 채워집니다. 없으면 `null`입니다.

나중에 게시할 때는 이 순서를 지킵니다. 먼저 비공개로 게시합니다. 소유자가 서명된 상태로 비밀번호를 한 번 설정합니다. 그 다음에 공개로 바꿉니다. 공개 상태의 사람에게는 서명된 신원이 붙지 않아, 비밀번호를 정하기 전에 공개로 바꾸면 이 단계가 열리지 않습니다.

로컬 `npm run dev`도 같은 로그인입니다. `cursor/identity.dev.js`는 이 허용 확인에도 사람 권한에도 쓰이지 않습니다.

## PWA

`app/manifest.ts`가 매니페스트를 만들고, 아이콘은 `public/icons/icon-192.png`, `public/icons/icon-512.png`입니다. 브라우저가 `beforeinstallprompt`를 주면 헤더에 **앱 설치**가 나옵니다. 그렇지 않으면 **홈 화면에 추가** 안내만 보입니다. iOS 설치는 이 환경에서 확인하지 않았습니다.

`public/sw.js`는 아이콘과 매니페스트만 캐시합니다. `/api/` 응답과 GET이 아닌 요청은 캐시하지 않습니다.

## 비밀값

이름만 바인딩되어 있습니다. 값은 이 환경에 없습니다. 사용자가 Cursor의 보안 입력으로 넣어야 봇 API와 스케줄 웹훅이 동작합니다.

- `BOT_API_TOKEN`: `POST`와 `GET /api/bot/...`의 헤더 `x-cursor-app-token`
- `SCHEDULER_TOKEN`: `POST /api/jobs/webhook`의 같은 헤더 이름

두 값이 없으면 해당 경로는 503입니다. 사람 화면은 이 값 없이 동작합니다. 사람 화면 요청에 앱 토큰이 있으면 403입니다. 토큰은 프론트엔드, URL, 로그에 넣지 않습니다.

## 스케줄

무인 스케줄은 켜져 있지 않습니다. 배포된 Cursor 앱이 서버 크론을 실행한다는 사실은 확인되지 않았고, 브라우저 타이머로 대신하지 않습니다.

같은 작업은 두 가지로 실행합니다.

- 관리 화면의 **지금 실행**
- `POST /api/jobs/webhook`에 `x-cursor-app-token: $SCHEDULER_TOKEN`과 선택적 `Idempotency-Key`

반복 발생과 알림은 키로 한 번만 만들어집니다. 실행 기록, 재시도 횟수, 마지막 성공, 다음 예정 시각은 관리 화면에 나옵니다. 실패했거나 예정 시각이 지났으면 경고가 보입니다. 코디네이터가 외부 루틴을 웹훅에 붙이기 전까지 작업은 자동으로 돌지 않습니다.

## 백업, 복구, 업데이트

`cursor-app.json`이 Postgres를 선언합니다. 배포하면 플랫폼이 `DATABASE_URL`을 넣습니다. 이 환경은 그 주소를 받지 않습니다.

자동 백업과 보관 기간은 Cursor Apps Postgres 문서에서 확인되지 않았습니다. 복구 절차를 제공한다고 말하지 않습니다.

스키마는 `migrations/001_init.sql`입니다. 배포 빌드의 `npm run build`가 `node scripts/migrate.mjs`를 실행하고, 적용된 파일 이름을 `schema_migrations`에 남깁니다. SQL은 업무 행을 지우거나 통째로 다시 만들지 않습니다. 로컬에서 `DATABASE_URL` 없이 `npm run migrate`를 실행하면 `migrate: nothing to do`입니다.

업데이트는 새 빌드를 배포하는 일입니다. 이 작업은 배포하지 않았습니다.

## 비용과 계정

데이터베이스는 앱이 존재하는 동안 과금된다는 점만 확인했습니다. 금액은 확인하지 못했습니다. 유료 제3자 서비스는 넣지 않았습니다. 푸시와 외부 메신저는 없습니다. 알림은 앱 안 수신함입니다.
